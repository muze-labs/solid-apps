# Capability-dialog UI implementation

Implemented on spiral/CYC-20261107-QG24H-49-capability-dialog-ui, from main
7fabcc1. Source SRC50 and design DES51 retain the confirmed goal. No commit,
merge, publication or human acceptance is inferred from this working-tree result.

## Shared design and ordinary UI

The private experimental @muze-labs/solid-design package reuses installed the-ds
0.2.7. It exports plain SimplyFlow dialog, dropdown and list/details datasets,
with prefixed public names and CSS. Account, Preferences and app composition
register the relevant components; there is no second renderer or component
merger. Headers have consistent close controls, optional titles, scrolling bodies
and visible action footers. Dropdown keyboard focus and hover use the blue accent.
Contacts uses shared responsive list/details panes with a visible lower toolbar.
Native focus, popover, dialog and browser navigation remain direct.

App globals use muzeSolidLauncherApp / muzeSolidContactsApp /
muzeSolidFilesApp / muzeSolidProfileApp. Existing solid-prefixed diagnostic handles
remain available. The account popover ID is prefixed. Local/scoped app state is
not mechanically renamed. Authored sources and source metadata retain the new
shared components through explicit feature barrels.

Launcher shortcut creation moves into a dialog. Advanced launch settings,
built-in app links, resource opening and app-instance permissions use labeled
disclosures. Real sync/save/conflict recovery controls are retained. Profile
source identifiers move into a disclosure; list item projections and native RDF
remain authoritative. Task mode removes irrelevant editing/deletion controls
and technical success messages from the Files picker.

## Capability presentation

Launcher resolves explicit built-in providers for browse and edit-profile.
The shared host creates a scoped transient ticket and transfers the existing
private MessageChannel connection after validating provider readiness, source
and origin. Broker operations bind the task to the registered caller; iframe
instances and keys are excluded from workspace snapshots, checkpoints and app
restoration. Registration/readiness does not stage spurious workspace saves.
The existing top-level broker/chooseFiles route remains supported.

Profile implements the edit-profile contract using its existing shared editor,
configured Metro client, native graph copy and conditional document save. It
only edits the connected account's own WebID. No domain editor is copied into
the caller. The caller validates the returned URI and reloads its own account
name; other open apps' automatic name propagation remains future work.

The task marker selects compact invocation UI while the same provider remains
standalone at normal URLs. Profile waits for its capability input instead of
loading the launch resource twice. A provider-ready handshake avoids delivering
the port before the app has installed its listener.

Interactive calls wait for completion or explicit cancellation. Outer Close and
Escape ask the provider about unsaved drafts and active saves. Saves block close;
drafts require explicit discard. Routing failures keep the live provider visible
rather than destroy its draft. Workspace checkpoints also refuse unsaved tasks.
If framing fails, a tab opened in the user's click continues the same waiting
capability request; completion reaches the caller and closes the transient tab.
Without Launcher, a normal standalone provider link remains available.

EVD53 records tests, captured layouts, size budgets and remaining evidence limits.
Registry/recipient work, named workspaces, automatic sync/PWA, live IDE/runtime
composition and stage-two collaboration remain outside this cycle.

## Provider-controlled loading (FBK62, confirmed design)

Host retains a full-size concealed/inert frame with a centered status/spinner.
Transport readiness remains separate. Providers can opt into waitForPresentation
and call ManagedApp.presentationReady after binding their initial request view.
Profile and Files opt in and also reveal connection/error UI when appropriate.
The ready notification is scoped to the current frame window/origin/task ID.
Legacy providers use native load plus transport attachment; promised but missing
readiness falls back after five seconds. Missing transport retains existing tab
recovery. Timers/listeners are cleaned up and reveal never steals focus. Error
recovery exposes an attached provider to preserve access to drafts. EVD63 records
validation, source limits and remaining human acceptance.


Presentation follow-up: loader/content opacity crossfade over 300 ms at reveal.
The loader becomes aria-hidden when content is ready and is removed after its
fade. Reduced-motion preference skips the fade. Reveals are idempotent, and fade
timers are scoped to the current call and cleared on connection cleanup so late
signals or closed invocations cannot restart or alter a later loading stage.


## Shared dialog motion (FBK64, confirmed reference effect)

Shared native lifecycle actions fade/scale dialogs from 0.7 to 1 and fade the
native backdrop over 300ms, reversing on close. Native close waits for exit so
modality/focus restoration remain intact. Reduced motion is immediate; phone
fullscreen remains below 720px. The bridge fills the Firefox deferred-close CSS
gap through native Web Animations, without replacing dialog semantics/rendering.
Simple dialogs use a shared scoped Escape behavior. Capability dialogs retain
provider save/draft guards and keep the frame visible until closing completes.
Account, Preferences, Contacts and Launcher commands reuse the same actions.
EVD65 records reference/API inspection and validation; acceptance remains pending.

Dialog animation completion has a 350ms cleanup bound for background tabs where
finish delivery can be deferred. Normal visible motion remains 300ms. The native
modal closes only after the animation or its bounded cleanup; reduced motion
skips animation. Browser fixtures activate pages before waiting for motion and
cover closing while the page remains hidden.
