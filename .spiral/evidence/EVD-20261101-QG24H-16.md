# Successful PUT without ETag verification

Date: 2026-11-01. Implementation `e2fe0dd`, feedback FBK15.

The maintainer's actual headers establish CSS returning PUT 205 without ETag,
then an authorized GET 200 with a strong ETag and ETag exposed through CORS.
The earlier GET 401 report was explicitly corrected to that authorized response.
This is decisive evidence for a client acknowledgement/preparation bug, rather
than a need to change the Pod's CORS configuration.

A predecessor probe reproduced the false failure: one acknowledged PUT, local
state already marked clean, followed by `Pod supplied no ETag for a safe write`.
HTTP permits successful PUT without a validator, including when transforming the
received representation:
https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.4

Verification on the corrected implementation:

- `npm run check` passes six test files and the four-app build. The workspace
  state file has thirteen direct contract cases.
- New contracts cover acknowledging 205 without ETag, deferring fresh-validator
  reads until another write, using the new GET ETag rather than the old one,
  retaining the acknowledged baseline across reload, preserving concurrent local
  edits during PUT, target isolation, real remote-change detection, and refusing
  unauthorized refresh without treating it as empty data or issuing another PUT.
- An ordinary-close attempt cannot reuse the stale pre-write validator. A GET
  genuinely lacking a readable ETag still refuses an existing-resource update.
  Unknown native RDF and private reconnect-data boundaries remain covered.
- `npm run test:browser` passes the full existing app suite and the complete
  managed-workspace proof. Every successful workspace PUT in that fixture now
  returns 205 without ETag, while GET returns its current strong validator.
  Repeated saves, acknowledged Save & close, fresh-browser restoration,
  checkpoint recovery, conflict review, conditional retry, RDF preservation
  and the ordinary-close fixture receipt all pass under this response pattern.
- Validation also checks that a fresh read for an explicit save does not silently
  replace the caller's live workspace with a different remote version. A first
  test run exposed that interaction; the forWrite read mode now retains it as a
  conflict requiring review, including when the local cache was previously clean.
- JavaScript gzip totals including auth callback: Launcher 192488, Contacts
  185469, Files 168812, Profile 185320 bytes; all below 200000.
- Spiral snapshot validation, new-reference ancestor/artifact checks and
  whitespace checks pass. No merge or publication was performed.

The actual-response evidence came from the maintainer. Automated writes remain
isolated fixtures; the agent did not access or modify the user's Pod. Successful
browser-X delivery remains best effort. If the most recent write lacks a new
validator, an ordinary-close attempt cannot fabricate one; local pending state
is retained until a fresh read. The local build is updated for another human
Save & close evaluation. Acceptance is pending and the cycle remains Active.
