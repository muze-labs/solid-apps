# Firefox tab/iframe authentication investigation

CYC49, FBK56. Actual branch checked:
spiral/CYC-20261107-QG24H-49-capability-dialog-ui. No product changes in this
investigation; no acceptance, commit, merge or publication.

## Effective installed contracts

metro-oauth2 0.9.3 tokenStore uses localStorage keyed by issuer + WebID as supplied
by metro-oidc 0.9.4. DPoP keys live in the origin's IndexedDB metro/keyPairs store,
keyed by issuer. Both are used through each app's normal Metro client. Account
restoration intentionally calls connectSession/perform with interactive:false;
it can use an access/refresh token but reports sign-in required if neither works
and a fresh authorization code would be needed. The message alone does not prove
why reuse failed. A cached identity token is also insufficient evidence.

The iframe is not sandboxed to an opaque origin. Same-origin localhost apps are
expected to see the same stores. Firefox partitioning keys use origin plus the
top-level site; generic cross-site partitioning does not explain this same-site
case. Sources inspected: installed middleware and Mozilla documentation at
https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/State_Partitioning and
https://hacks.mozilla.org/2021/02/introducing-state-partitioning/ .

/tmp/cycle49-auth-reuse-probe.log. Firefox 157.0.1, geckodriver 0.37.1, fresh
WebDriver-owned profile. All resources/tokens belong to a synthetic local fixture;
no live credentials, browser profile or user Pod is accessed.

A local HTTP server serves the current built Profile app and a public WebID with
protected preferences. Installed Metro OIDC/OAuth/DPoP middleware is real. The
fixture seeds cached client metadata, a synthetic identity/access/refresh token,
then checks real signed ES256 DPoP proofs and matching public key for requests.
It first loads Profile in a normal tab, then Profile as a same-origin task iframe.

- Tab restores the account and reads protected preferences with a DPoP proof.
- Task iframe independently restores the same account, reuses the cached access
  token and the same persisted DPoP key, and reads protected preferences.
- Expiring the synthetic access token and reloading the task causes exactly one
  silent refresh-token exchange. The refreshed token uses the same DPoP key and
  the protected read succeeds without interactive authorization.

The iframe probe uses the actual shell/session code but no broker request, user
login or live issuer. It establishes baseline storage/access/refresh reuse, not
that the maintainer's failure is solved. Initial probe attempts hit a stale iframe
reload read; the corrected probe passes all assertions. WebDriver session deletion
succeeds; attempting to signal the snap driver afterward reports EACCES, retained
in the log separately from product/probe assertions.

## Remaining uncertainty

The reported failure is not reproduced with healthy cached tokens in Firefox.
Requested a read-only live Launcher/iframe diagnostic reporting exact origins,
account/issuer equality and access/refresh/identity token presence/expiry, without
credential values. Also asked whether the profile/edit UI appears despite the
status message. This distinguishes missing or differently scoped caches from an
actual protected-request rejection or stale startup status. Do not implement a
new session-sharing mechanism without that evidence.


## Live evidence and exact-state reproduction

The maintainer's diagnostic confirms identical origin (http://localhost:4174),
account and issuer. Both contexts see an expired access token, no refresh token,
a cached identity and no legacy issuer-only token. Profile content/Edit appear.

Extended the disposable Firefox probe to expire the access token and remove its
refresh token, reload the task, then read the public profile through the actual
Profile showRemote action. This reproduces the reported outcome: private
preferences return 401, background authentication raises Sign-in required, and
public profile/Edit still appear with that earlier status left visible.
Log: /tmp/cycle49-auth-reuse-expired-probe.log. Cached access and silent refresh
cases still pass before this exact-state reproduction. No live Pod writes.

Cause established for this report: authentication storage is shared, but neither
context has renewable resource authorization. The startup status comes from
protected preferences and persists even after the public profile is displayed.
The diagnostics do not independently establish a working protected write in a
normal tab. An ID token or public profile read is insufficient evidence of that.

## Refresh authorization gap and proposed correction

Installed metro-oidc defaultScope requests openid webid for this composition;
connectSession supplies no scope override. The previously fetched public
Solidcommunity discovery advertises offline_access and refresh_token support.
The Solid-OIDC primer says offline_access requests refresh-token issuance:
https://solid.github.io/solid-oidc/primer/ . OIDC Core section 11 additionally
requires consent handling for offline access:
https://openid.net/specs/openid-connect-core-1_0.html#OfflineAccess .

Thus missing offline_access is a concrete configuration gap and likely explains
absence of a refresh token, but no live token issuance was inspected to prove
that provider-specific causal step. Requesting the scope does not guarantee
issuance. A fresh authorized login is needed to obtain a missing refresh token;
existing expired credentials cannot silently become renewable.

Recommended next correction: configure refresh authorization through Metro's
public scope option, support required provider consent, preserve silent reuse
when valid tokens exist, and provide explicit reauthorization when they do not.
Make startup preferences failures specific rather than suggesting the public
profile could not open. Do not clear unrelated failures or lose edit drafts.

Another installed integration gap: perform's popup-reservation condition uses
presence of an ID token, not usability of access/refresh credentials. With cached
identity and expired access/no refresh, the popup is attempted only after the
protected request responds, which risks losing the browser's user activation.
Profile onSave also awaits RDF copying before perform. This is a code-observed
risk, not a reproduced popup-blocking result in the maintainer's session.

Metro's OAuth configuration supports prompt, but the installed OIDC middleware
does not forward an app-supplied prompt into that configuration. Confirm a
supported consent path before implementing a partial offline_access fix; do not
invent a second authorization stack. Product auth changes remain proposed in this
investigation, not implemented or accepted. No test/build changes were made.


## Recovery UI and silent authorization discussion

Maintainer confirms reconnect succeeds. OIDC prompt=none can attempt an existing
issuer session without showing login/consent UI and may return login_required,
interaction_required or consent_required. It is distinct from token refresh:
https://openid.net/specs/openid-connect-core-1_0-errata2.html#AuthRequest .
A hidden issuer frame is cross-site even though the suite provider frame is
same-origin. Firefox cookie partitioning and provider framing policy can prevent
issuer-session reuse; no live Solidcommunity hidden-frame success is claimed.
https://support.mozilla.org/en-US/kb/total-cookie-protection-and-website-breakage-faq .

Proposed behavior, not accepted/implemented: reuse/refresh through Metro first;
optionally make one bounded prompt=none attempt where supported; then offer a
nonblocking contextual Sign in again action and preserve drafts. Protected saves
can expose Sign in and save and resume the same conditional operation after
explicit recovery. Network/server errors must not be labelled session expiry.
Existing OIDC prompt forwarding and iframe authorization lifecycle would require
library support; do not build a parallel suite authorization transport.
