# Managed browser-local workspace revision

Retained maintainer direction, 2026-11-01. During evaluation of the initial
server proof, the maintainer objected to the server bottleneck and asked about
a browser service worker. A disposable Chrome 131 probe showed separate worker
and IndexedDB instances when the same broker origin was embedded under different
top-level sites. A second probe established cross-origin messaging, explicit
child closure and cooperative child shutdown using an ordinary opener.

The maintainer proposed using Launcher as the broker and lifecycle owner:
closing Launcher closes its managed apps, reopening restores them, and apps
publish their state to Launcher. They explicitly accepted retaining opener.

Asked whether the current cycle should be revised around this browser-local
managed-workspace model, replacing the server relay, the maintainer replied:

> Yes. And lets test whether we can store the state in the users storage pod
> as well, not continuously, but at least when closing the launcher.

This supersedes the earlier requirement for managed apps to communicate while
Launcher is closed. Standalone use remains useful. The Pod-on-close request is
an empirical requirement: distinguish an acknowledged explicit close/save from
best-effort browser-tab closure, and preserve local state when network work
cannot finish. Browser callbacks and popup restrictions were explained before
the maintainer confirmed the revised frame.

The temporary probes live under `/tmp/solid-apps-service-worker-probe.mjs` and
`/tmp/solid-apps-managed-window-probe.mjs`. They are bounded Chrome evidence,
not a claim about all browsers or crash/mobile shutdown.
