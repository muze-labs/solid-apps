# Native Turtle persistence and a narrow opaque-state experiment

Direct maintainer instruction, 2026-11-01:

> Make a note: never under any circumstance write a string with json inside a turtle file. If you cannot find a way around it, explain the issue and we'll resolve it together. For solid apps turtle is the native format.

This is a mandatory project constraint, not a preference. Main persistent
structures must use native RDF terms and statements. If representation is
unclear, explain the obstacle and resolve it with the maintainer before writing.
Do not evade the native-format requirement by moving application persistence to
JSON files. The later explicit exception below is narrow and experimental; it
does not authorize generic JSON snapshots, caches, baselines or migrations.

Inspection finds current noncompliance in workspace-state.mjs: setJSON writes
both the Pod snapshot and the local cache as JSON literals, including a serialized
baseline. The managed-workspace design and tests also describe/use that encoding.
There is a straightforward native RDF direction for workspaces, app instances,
resource links and individual UI/draft fields. This note does not claim an
implementation or migration has happened. Existing data must not be destroyed.
The instruction supersedes the JSON-literal design; its design and implementation
are flagged as noncompliant pending native RDF correction. The cycle remains Active.

## App-owned opaque state clarification

The maintainer subsequently clarified:

> for the app state, I can imagine that not everything will be linked data. In that case we need a separate opaque string that the application can resolve itself, in whatever way it likes, but the main state should be linked data

The main state remains linked data. An app may additionally supply an opaque
string with app-defined meaning, preserved without broker interpretation. This
is not a substitute for the native RDF main state. The meaning of JSON inside
that field was clarified explicitly below. No runtime change or migration is
implemented by this rule-note update.


## Explicit experimental exception

After being asked whether the opaque app-owned field may contain JSON, the
maintainer answered:

> This is a case where I'll allow it, if only to test that it works. But it is ugly, other people will object to dirtying a turtle file like this.

Only the separate, optional app-owned opaque string may experimentally contain
JSON. The app owns its interpretation; the workspace/broker preserves and returns
it without parsing or normalizing its contents. The main state stays linked data.
This is not permission to encode whole workspaces or persistence baselines as
JSON strings, and does not make JSON-in-Turtle a recommended practice. Retain the
maintainer's objection and the explicitly experimental status. Verification of
this interoperability exception belongs with the eventual format correction.
