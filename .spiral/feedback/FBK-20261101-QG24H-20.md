# Finish the file-picker activation flow in this cycle

The maintainer reports that Choose in Files shows only a waiting cursor and asks
why Files must already be open. They confirm that manually switching to Files
reveals the picker controls: routing works, but the tab is not focused.
After discussion of focus and on-demand opening, they request:

> please keep it in this cycle.

A disposable cross-origin browser probe using the actual broker/client modules
and no workspace persistence reproduces the problem: the request arrives in
Files while Launcher stays focused; selecting returns the URL but leaves Files
focused. Code has no activation call in either request/response path.
The roadmap places existing-provider communication in Phase 1 and registry plus
on-demand startup in Phase 2. The maintainer explicitly extends this cycle to
include the bounded Launcher-to-Files startup flow, not the full registry.

Keep CYC2 open for correction: Choose in Files should focus an eligible existing
Files instance, or open the built-in Files app synchronously from the user's
click and wait for its verified ready connection. Reuse a saved built-in instance
when appropriate. Keep explicit per-instance grants, reject ambiguity, respect
popup policy, support cancellation/readiness failure, and return focus to the
Launcher on selection/cancellation. Do not invent a remote provider registry or
silently grant an existing denied instance.

The prior acceptance remains historical evidence for the earlier snapshot; this
new correction awaits evaluation. DEF18 stays Open, and the native RDF rule is
unchanged. This work changes activation/routing, not the persistence encoding.
Verification must avoid exercising the known noncompliant workspace serializer;
use isolated protocol/UI-intent fixtures without writing JSON inside Turtle.
