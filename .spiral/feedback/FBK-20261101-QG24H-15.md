# Acknowledged PUT without ETag is reported as a failed save

Maintainer report: `workspace-state: Pod supplied no ETag for a safe write.`
The maintainer supplied Community Solid Server response headers:

- PUT: HTTP/3 205, no ETag, Access-Control-Expose-Headers includes ETag.
- GET: initially reported 401, then explicitly corrected to HTTP/3 200, with
  ETag `"1793540863651-text/turtle"` and Access-Control-Expose-Headers including
  ETag. The corrected authorized response is the relevant read evidence.
- Both responses allow the local app origin. No credentials were supplied.

The client reproduces this with an acknowledged 204/205 PUT lacking ETag: it
marks state clean, then immediately prepares another write using a missing new
validator and throws. This falsely reports a completed save as failed. Reusing
the old ETag would instead produce a spurious conflict. HTTP does not require
an ETag on successful PUT; transformation can prohibit returning a validator:
https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.4
The supplied GET exposes a strong validator, so no CORS/server change is needed
for the evidenced behavior. Solid's CORS header rule is documented at:
https://solidproject.org/TR/protocol#server-cors-access-control-headers

Correct the same cycle: retain acknowledgement independently of the availability
of a validator for a future write. Refresh the native document before the next
write when its validator is unknown, without reusing the pre-write ETag. Retain
the acknowledged snapshot baseline locally so new local changes do not create
false conflicts against that same acknowledged remote state. Still detect real
concurrent changes, preserve unknown RDF and reject genuinely validator-less
GET updates. An unauthorized read must remain a read failure, never an empty
workspace. Closure writes may only use an already-prepared safe validator.
