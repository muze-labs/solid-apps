# Same-origin capability authentication reuse

After FBK54's URL correction, maintainer reports Profile dialog message:
`solid-app-data: Sign-in required. Click Connect Solid to continue.`
They request investigation because apps opened in tabs do not exhibit the same
problem, and capabilities should reuse existing authentication/authorization.
Browser confirmed: Firefox, dev setup via npm run dev on localhost; all apps
expected to share origin. Exact live origins/token state not yet observed.

The request authorizes investigation within active CYC49. Do not treat a remembered
WebID as evidence of a usable access/refresh token or assume a browser partitioning
problem. Do not route OAuth credentials through capability messages or weaken
issuer/account/key validation. EVD57 records direct Firefox comparisons and the
remaining live-session diagnostic request.


## Live diagnostic returned

Maintainer reports both contexts at http://localhost:4174, sameAccount=true,
sameIssuer=true, session=true, accessToken=true, expired=true,
refreshToken=false, identity=true and legacyAccessToken=false. Profile content
and Edit profile button are visible despite the status. No credential values
were supplied. This establishes a shared but expired cache, not missing iframe
storage. The UI status must not be interpreted as proof of blocked profile access.


Maintainer confirms explicit reconnection fixes the issue. They now ask for UI
design for expired authorization, including a possible hidden-iframe attempt
before requesting interaction. This is design discourse, not approval of a new
silent-auth implementation or refresh-token consent policy.
