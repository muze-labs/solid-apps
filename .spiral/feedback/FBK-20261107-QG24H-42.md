# Own-profile email projection shows objects and a resource reference

Date: 2026-11-07. Evaluation feedback within Active CYC-20261107-QG24H-37.
The maintainer reports the own-profile viewer/editor displaying:

> Email addresses
>     [object Object]
>     https://auke.solidcommunity.net/profile/card#id1673612040213

## Investigation and bounded scope

Before implementation, synthetic native RDF fixtures reproduce the object string
for both blank and named contact nodes whose vcard:value/hasValue is a NamedNode.
The reader calls String() on that nested node. A linked contact node without a
recognized value is instead presented as though its resource ID were an address.
The same conversion exists in the accepted-main baseline; do not attribute its
origin to the new model code without evidence.

The supplied public profile document was read anonymously through the configured
Metro client (oidc disabled), not browser credentials or an app-owned fetch path.
The document returned 200 and contains two named email references: one has a
vcard:value mailto node, the other has no describing predicates. Only predicate
names, value kinds and result counts were printed; no address is retained in
this feedback. No actual Pod data was changed and no extra linked documents
were fetched.

Correction: follow supported vcard:value/hasValue terms in the current graph,
project their scalar/IRI values and strip the mailto/tel scheme per leaf. Preserve
multiple values and stop on cycles. Unresolved contact resources contribute no
email/telephone text; they remain in native RDF and are treated as unsupported
structure for editing. Preserve all native statements during unrelated edits.
This corrects the shared reader used by Contacts, Profile and account metadata;
it adds no structured editing or deletion/migration policy.

No new cycle or acceptance is inferred from this feedback. The correction and
verification remain on the existing cycle branch; EVD43 records results.
