# Save & close stays blocked after a Pod conflict

Maintainer feedback, 2026-11-01: Save & close opened an apparently idle window.
The single-line message was lost while reloading, and later clicks appeared
ineffective even after reload. The maintainer subsequently recovered the exact
error: `workspace-state: Pod conflict; local state is retained.`

Code confirms that conflict refusal preserves data, but there is no user-facing
resolution path. Reload reloads the same dirty local state and differing remote
snapshot, then refuses again. Errors appear only in the header and vanish on
reload. Interactive session.perform reserves an authentication popup before
local checkpoint/conflict validation, explaining an otherwise idle window on
some failing operations. The actual origin of the differing Pod version is
unknown; it may be another session or an unconfirmed close-time write.

This is correction of the existing cycle outcome, not a new cycle or acceptance.
Provide progress/errors beside Save & close, retain the last failure on reload,
and allow explicit review of local/Pod state before choosing one. Keeping local
must write conditionally against the reviewed Pod version, preserving unknown
RDF. Using the Pod version must explain that it replaces the managed session.
Ordinary saves must never silently override conflicts. Local state/restoration
must stay usable when remote preparation fails. Preflight known conflicts before
opening an authentication window.
