# Shared UI with embedded capability providers

The installed the-ds 0.2.7 already supplies dialog header/content/footer,
dropdown and list/details primitives. Reuse them through a private solid-design
package, registered by the shell, Preferences and apps, rather than creating a
published library or another rendering system. This avoids a dependency from
Preferences back into the shell while allowing the same component datasets to
be reused. Native dialog/frame
lifecycle remains direct; markup and dynamic attributes use SimplyFlow.

Use the existing PortConnection and ManagedApp interfaces. Launcher owns routing
for transient embedded provider instances. A registered caller requests a scoped
embedding ticket for an explicitly configured capability/provider URL. The caller
transfers a private port to Launcher and the matching port to the iframe using
exact target origins. Launcher validates ticket, owner window/origin and one-time
attachment. Transient instances do not enter workspace snapshots/checkpoints.
No OAuth tokens, shared graphs or user write credentials are transmitted by
the capability protocol. Same-origin pages retain ordinary browser-origin
access; this presentation is not a credential sandbox.

Profile advertises an edit-profile capability with a target subject URI; it loads
and conditionally saves via its own existing Metro/RDF flow. A successful result
identifies the profile URI; the caller refreshes its own view. Files keeps browse
semantics. Embedding is a presentation option, not a new domain protocol.

The host owns generic chrome, iframe and close/fallback controls. Provider pages
own edit/selection controls and visible footer layout. Closing asks the provider
whether drafts or in-flight saves need attention; explicit discard is separate
from safe close. Browser framing/login behavior needs runtime evaluation; keep
an explicit top-level provider link when embedding cannot proceed. No OIDC
implementation changes are included.


Implementation refinements established by runtime evidence:

- The provider announces readiness after installing its ManagedApp listener;
  frame load is insufficient because asynchronous app initialization can finish
  later. The host verifies both source window and exact configured origin.
- A dedicated task URL flag works in a frame or a user-opened tab. Framing refusal
  offers a tab that continues the original pending call, not just an app link.
  Standalone apps without Launcher retain an ordinary provider link.
- The current task can close only after checking provider draft/save state.
  Broken routing keeps a live provider visible for recovery. Transient instances
  never become saved apps or reopen through workspace restoration. Checkpoints
  refuse unsaved tasks, and interactive calls have no arbitrary one-minute limit.
- Common panel sizing must match panes through SimplyFlow's display:contents
  wrappers; a direct-child selector misses the actual list pane. Mobile footer
  controls and title/account separation receive explicit viewport assertions.


## Confirmed dialog motion refinement (FBK64)

Apply the SimplyEdit backend's reference fade/scale effect to shared native
modal lifecycle: 300ms opacity/scale(0.7) to normal size plus backdrop fade,
reversed for closing. Preserve the existing below-720px fullscreen layout and
skip motion for reduced-motion preference. Native modality/focus remain until
closing completes. Capability cancellation continues through its save/draft guard;
simple dialogs can share an Escape behavior. Firefox lacks CSS overlay transition
support, so use native Web Animations for this narrow lifecycle gap, retaining
SimplyFlow rendering. EVD65 records API evidence and cross-browser checks.
