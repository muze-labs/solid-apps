# Refresh-first recovery

The maintainer confirms: "Yes, use refresh-first recovery" after presentation
of the current behavior and gap. This authorizes implementation in CYC67.

Use Metro's existing silent refresh, stores, DPoP and OIDC validation. Decorate
its authorization URL with offline_access and consent only when discovered
metadata advertises support. No discovery is added before public reads.

Metro 0.9.x lacks typed refresh errors/fresh-login fallback. A narrow transport
middleware identifies only a token-endpoint refresh HTTP 400 invalid_grant,
retires that rejected credential through public stores and raises a typed error.
The resource client's outer middleware retries the single challenged request
once, with its original body and conditional headers. Never replay an app
operation, earlier writes, network errors or access denials.

Background restoration reports sign-in required without opening a window or
waiting for user action. Public content remains usable. Interactive authorization
can wait for a shared accessible recovery dialog, which reserves a popup on the
user's sign-in click. Cancel rejects the pending request and retains drafts.
Explicit recovery without a pending operation uses a forced authorized profile
GET without calling onConnect, reloading app data or resetting Preferences.

Recovery presentation is a named SimplyFlow feature with prefixed names. Reuse
the shared native dialog, motion, focus and toast components. Persistent recovery
is contextual; temporary success is a toast. Sign-in errors remain actionable.
Hidden-iframe authorization is deferred. Provider issuance of refresh tokens is
not guaranteed. No credential is sent over capability messages.

CUL-MUZE-001 and CUL-MUZE-LIB-001 apply to the suite's shared packages: readable
features and a limited documented bridge, no second authentication implementation.
WPF-HUMAN-001 composition/evidence concerns are addressed by typed narrow failure
classification and explicit limits on synthetic-provider evidence.

## Shared authorization and cancellation

Storage events notify another same-origin app of renewed authorization through
Metro's existing account-scoped stores. Clear stale notices without reloading.
If authorization was waiting for a user action, release that callback with a
typed authorization_changed signal and retry only the challenged request with
the newly stored token. If a popup exchange is already underway, let Metro
finish it. Keep denied access and conditional-write conflicts visible.

Preferences recovery loads a missing baseline but preserves open form values;
an already loaded form is left intact. Operation counters prevent concurrent
background/interactive operations from resetting authorization policy or closing
a shared popup while another operation is still using it.

The recovery behavior reuses shared dialog actions/styles and owns cancellation.
A non-cancellable native CloseWatcher event must complete natively; scheduling
another animated close would risk closing a subsequently reopened dialog.
The phone presentation is fullscreen with bottom actions and a visible close
button; existing shared motion and reduced-motion handling remain in use.

Primary standard checked during this cycle:
[OIDC Core section 11](https://openid.net/specs/openid-connect-core-1_0.html#OfflineAccess).
Offline authorization needs appropriate consent; requesting it does not prove
that a real provider has issued a refresh token. Lazy discovered metadata comes
from Metro, and token/identity validation stays in Metro.

These artifacts remain uncommitted. Exact version references between new
artifacts can be recorded when semantic commits are explicitly requested; no
placeholder commit hashes are invented.

## Cancellation after the popup returns

A controlled delayed-token probe reproduced a queued PUT after recovery was
cancelled while the token response was pending. The token callback alone cannot
cancel an exchange once it has returned a code. Metro has no public per-request
authorization-cancellation context, so the suite composes its configured client
per resource request with a transport gate that captures the session cancellation
count. It checks before dispatch and after a token response. Cancelling changes
the count; older attempts cannot dispatch further requests, while a later retry
uses the new count. Token exchange/validation/storage remain library-owned.

A successful dialog close does not mean cancellation. Only explicit cancel,
native cancel or component cleanup cancels the authorization attempt. Already
sent writes cannot be retracted by this gate; ordinary save/close guards and
conditional-write handling remain authoritative once a write is dispatched.
Intentional cancellation is not rendered as a persistent error.

If the initial Preferences read failed, Save first recovers its missing RDF
baseline inside the same session operation, retaining the form values. It then
performs the existing conditional native save; it does not reconnect the app.


## Shared confirmation motion after live evaluation

The maintainer verifies the live recovery action/toast, but requests toast motion.
The current component toggles hidden immediately; no shared lifecycle animates
entry or exit. Add CSS opacity/vertical-transform transitions lasting 300ms,
with starting-style for entry. SimplyFlow binds a prefixed closing attribute;
the hide action retains content for the exit, then clears it. A replacement
clears the old timer and closing state, preventing a stale exit from hiding it.
The existing eight-second lifetime and hover/focus pause remain unchanged.
Reduced motion skips transitions and the exit wait. Restore focus before making
an exiting toast inert; keep the existing polite live region and dismiss button.
This is a contained refinement, with no new renderer or animation framework.
