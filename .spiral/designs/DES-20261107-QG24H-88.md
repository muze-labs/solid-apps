# Feature-owned styles and supported runtime boundaries

Design for confirmed CYC87; initial investigation and its resolution are retained
below. Inspect the currently
installed/published SimplyFlow APIs before choosing a runtime update mechanism.
Keep SimplyFlow responsible for runtime rendering; avoid a new CSS/DOM updater
or generic component runtime. Preserve cascade and both ordinary and embedded
first use. Split source by coherent feature ownership and remove migrated
redundant delivery; do not combine with a visual redesign or mass prefix rename.

Current named style ownership: suiteAppearance imports the entire solid-app-ui
style.css as suite-appearance. Existing solid-design components and Preferences
form already expose their styles in named entries. Build also copies the entire
shared stylesheet into apps.css and links it before startup. Its early CSS and
later inserted component styles both participate in the effective cascade;
removing the external copy without checking first paint/order is not equivalent.

The installed app package installs CSS only during construction; its style lookup
also uses an unescaped dot selector while emitted IDs include .css. No supported
live replacement/removal API was found in installed app/bind source or README.
Do not work around that with app-owned rendering. Probe current registry support
and settle any necessary library scope before a full live-style contract.

Readability, existing native operations/RDF/session rules and the fixed JS budget
remain constraints. Budget baseline: Workbench minified 133921/readable 196147 B;
Contacts 116900/175788; Files 120138/179438; Profile 116536/175447. The coarse CSS
is 15033 raw / 3442 gzip bytes, already present in runtime JS and separately in
apps.css. Do not wrongly add that whole amount to an already-inclusive JS graph.
Measure real outputs rather than infer compressibility from source partitioning.


## Supported live-style contract to resolve

The actual built Contacts probe establishes that editing named component source
is not a runtime visual override. Current npm registry versions remain app
0.10.3 and facade 0.10.4. A library change, if included, should expose supported
updates to effective named CSS in a running instance; preserve the existing
style position/order while replacing its content; restore the original CSS
without duplicates; handle names/generated .css IDs correctly; and own native
style node lifecycle/cleanup. Keep personal override persistence/stack selection
and live template composition outside that narrow rendering contract.

The maintainer is asked whether to include lower-library live-style support
first or complete source ownership with live updates explicitly deferred. That
is a material scope choice: this monorepo consumes published npm versions, and
existing work in other repositories is outside the authorized suite change.
No library edit, release, dependency update or app-owned updater is performed
while that choice is pending. Pure ownership/cascade analysis continues.

## Delivery and cascade uncertainty

apps.css loads before module startup, then SimplyFlow inserts shared and app
component styles into their containers. The external early sheet and later
coarse runtime copy are identical source but have distinct positions. A migration
must check both initial rendering and loaded views; removing a delivery path is
not safe solely because a later final screenshot looks correct. Maintain useful
View Source and one authored source per rule while choosing supported delivery.
No bootstrap renderer, custom stylesheet updater or hiding meaningful first-use
cost is authorized as a shortcut.


The maintainer resolves the scope question: "SimplyFlow also add style elements
with an id linked to each named style. So the IDE can easily find the linked
style element and update that as well." The existing name-to-style-element
mapping is sufficient. Proceed with feature ownership in this suite; the future
IDE coordinates source edits and installed style content using that mapping.
No new SimplyFlow API, dependency, external repository edit or app-owned runtime
updater is needed. Tests may simulate IDE edits/restoration through those named
style elements. Earlier library-support-first conclusions are superseded by this
explicit clarification, without claiming metadata mutation alone is reactive.


## Implemented direction after the clarification

The user's ID-linking clarification resolves the consequential choice. Split CSS
into existing feature datasets using the installed text-import/styles mechanism;
keep the same selectors, declarations, related media rules and relative ordering
within each feature. Use new swb- style names. Retain generic palette/forms/layout
in suiteAppearance; put Contacts icons/list/search/layout, shared Profile
view/editor, Workbench shortcuts/workspace, Files table/editing/picker and shared
account/capability/recovery presentation in their respective existing features.
Shared dialog/list-details primitives join their existing design components.

Delete the retired coarse stylesheet and apps.css copy/link; no second compiled
source is maintained. SimplyFlow synchronously installs styles before binding
its templates. Check the core first-use task under the same cold network fixture,
in addition to loaded-view comparisons. Keep third-party the-ds CSS external.
No runtime app updater is introduced. Test code simulates an IDE by preserving a
source override and replacing the already linked style element's content, then
restoring both in place; original component definitions remain untouched.

A before/after workflow capture records 37 computed CSS properties for laid-out
nodes and same-origin iframe content alongside screenshots. It identified an
embedded Profile toolbar hiding rule initially assigned to Files due to its
selector name; that rule was corrected to the Profile resource feature. This
shows why a broad passing functional suite alone is not the visual acceptance
criterion. Further ownership checks move Contacts-only icon buttons and the
Profile-only resource URL to their actual owners. No UI redesign is included.


Final ownership audit also keeps generic compact person-list button spacing in
the shared foundation because Workbench uses that list too, and gives the
Workbench resource-selection feature its own launch-profile styles. The final
CSSOM inventory accounts for every original rule and the final view comparison
matches across all captured states. No new renderer or library API is required.
