verified connection/authentication with solidcommunity.net and prioritized the

Governing plan: `design/solid-capability-broker-roadmap.md`, Phase 0. Current

## Plan

Goal: a launcher link carries its current WebID and a complete resource URL to
Profile, which opens the requested RDF subject with its fragment preserved.
Document and test shared encoding/decoding for later independent consumers.
The maintainer clarified during execution that each launch opens a new app
window, leaving Launcher and existing app windows intact. During local testing,
the maintainer corrected the presentation preference to a new tab by default.
The maintainer then requested a user preference for tabs or windows. The shared
Pod-backed Preferences dialog now offers that choice, defaulting to tabs.
During evaluation, the maintainer requested optional
`#app-fragment?webid=...&resource=...` support: parse only the part after the
first literal `?`, then leave `#app-fragment` in the address. This is an explicit
extension of the same launch contract, with legacy-format compatibility.
The maintainer subsequently requested explicit query mode for server-side
apps, correcting the default to **user override > application declaration >
fragment**. Users must be able to alter existing shortcuts and return to
following the app. This extends the same launch-interface cycle; application
description discovery and broker work remain outside scope.
The maintainer then requested anonymous launches and clarified that the choice
is saved per launch link, since an app can have multiple links. The outgoing
URL must omit WebID and include resource only when specified. This is a saved
per-link exception to the current-WebID rule, not a change to the receiving
application's session policy.

Commitment: the maintainer clarified full resource URLs and current launcher
WebID, then answered "agreed" to the concrete Launcher-to-Profile proposal in
`../launch-context-proposal.md`. That confirmation settles the first slice.

Plan continuity: **continue** the governing roadmap's Phase 0. Do not treat this
slice as completing all Phase 0 contracts or authorizing broker work.

Evaluation: a real browser launch opens the intended subject, includes the
current WebID, preserves nested URL fragments and performs no implicit write.
Invalid input fails clearly. Standalone startup and local `?contact=` links
continue to work. Run project checks and browser tests.

Likely work: a shared launch URL codec, Launcher interaction, explicit launch
handling and readiness in the shared shell, Profile loading, contract docs and
failure/preservation coverage. Keep assumptions in this monorepo.

Non-goals: broker, registry, grants, clipboard, Open With recognition, app
publication, and loading alternate Contacts datasets or Files resource modes.

Boundary: one observable end-to-end proof is enough to evaluate this missing
interface. Stop/replan if the interface needs implicit authority, destructive
data mixing or a change to the standalone authentication contract.

## Act

Implemented:

- `packages/solid-app-data/src/launch.mjs`: shared HTTP(S) launch URL codec,
  preserving nested fragments and rejecting unsafe or ambiguous input.
  The additional `parseLaunchUrl()` operation returns decoded context and a
  remaining URL without mutating its input. `readLaunchContext()` retains its
  original context-only return shape. An optional app-fragment prefix is
  preserved by both parser and builder.
- Launcher: current-WebID app links and a profile-resource launch form. Each
  launch requests a fresh target with `_blank` and `noopener`. Tabs are the
  default; a shared `apps:launchTarget` preference selects windows with `popup`.
  The browser probe checks both presentations and preference reload persistence.
  Saved launch shortcuts receive the current WebID without changing their RDF.
  App descriptions can declare a parameter location; per-shortcut user overrides
  are separate RDF literals. Add and existing-row controls default to Follow
  application. Query mode reaches the HTTP query and clears stale launch fields
  from the inactive location while retaining unrelated application state.
  `apps/launcher/src/shortcuts.mjs` keeps this policy in the application layer.
  Each saved link also supports `apps:anonymousLaunch` as an RDF boolean.
  Both mode override and anonymity have explicit scalar replica policy; the
  application's declaration remains separate. The codec can generate an
  anonymous URL by omitting WebID and removes stale reserved identity fields
  from either parameter location. Resource is included only when supplied.
- Shared shell: opted-in launch context, background startup readiness, visible
  invalid/account-mismatch states and consistent handling of changed fragments.
  Prefixed fragment queries are consumed through history replacement, preserving
  the entry, state and app fragment. The address comparison baseline accounts
  for that consumption so ordinary later anchors do not erase the active launch.
- Profile: opens the exact requested RDF subject after account setup; preserves
  manual controls and local contact links, and retries after explicit connection.
- `design/solid-app-launch-context.md` and package/README documentation explain
  the contract to independent consumers. The governing roadmap's unsupported
  "already implemented" assumption is corrected prospectively.

Meaningful implementation correction: Chrome does not rerun page startup when
only the URL fragment changes. The first browser run exposed this; opted-in
receivers now reload on changed decoded launch context, retaining ordinary
anchor behavior when context is unchanged. Browser synchronization also waits
for rendered state rather than treating module availability as rendered UI.

The query-mode integration test also reproduced a settings-removal defect:
clearing an override locally was undone by replica sync because the predicate
had not been declared single-valued. The app's collection composition now
lists only the user-override predicate as a scalar setting. No library default
changed; app declarations and unknown metadata remain separate. The browser
test verifies set, sync, reload, clear, sync and reload before using the
restored declaration to launch the server-side app.

Warnings applied proportionately: URL identity grants no authority (W2), the
two-window result is verified as a composition (W4), and mock-Pod evidence is
not generalized into live-provider guarantees (W3).

Source/intent and acceptance are
recorded in this cycle and the confirmed proposal; downstream exact-version
causal links cannot be created until their upstream local commits exist.
No placeholder or foreign causal hashes were introduced.

## Evaluate

Integrated result: the browser opens Launch Alice from a full resource URL
containing both a query and subject fragment in a separate Profile target.
Launcher stays at `/launcher/` with its session intact. The new target has no
opener and receives the current WebID. Resource bytes and preferences remain
unchanged and launching adds no PUT requests.

changed launch fragments, invalid/duplicate values, missing subjects, denied
reads, account-mismatch recovery, local `?contact=` compatibility, saved launch
account replacement, and withholding saved launch context when disconnected.
The optional fragment-query extension was reverified with `npm run check` and
the full browser suite: the resource opened after cleanup to the encoded app
fragment, history state and length were preserved, and an ordinary anchor
change performed no reload or extra Pod request. Invalid prefixed parameters
left the address unchanged. Codec cases cover literal versus encoded question
marks, opaque prefix data, empty suffixes and intact nested resource URLs.

Query-mode extension verification: all project checks and the browser suite
passed again. The server-side fixture actually received `webid` and `resource`
as HTTP query parameters, including the resource's encoded query and fragment.
App declaration, user override, fallback to fragment, persistence and clearing
of overrides, inactive-location cleanup and unrelated RDF preservation are
covered. Unknown/structured user settings fail before graph mutation. A valid
explicit override can supersede an unsupported declared mode without altering
the declaration. Desktop/mobile captures include the new controls and the
mobile layout has no horizontal overflow.

Anonymous extension: `npm run check` and the complete browser suite passed.
Tests exercise two links to the same application with different saved identity
settings, true/cleared/true persistence through sync and reload, anonymous HTTP
query receipt while Launcher is connected, no-resource receipt with neither
reserved field, and a logged-out anonymous Profile launch with no parameters.
RDF boolean lexical values are read without flattening strings, structured
settings or multiple values. The checkbox is a SimplyFlow boolean binding.
The UI and contract explicitly scope anonymity to the outgoing URL; existing
receiver cookies and remembered sessions are not changed.

Launch-presentation preference: `npm run check` and the browser suite passed.
Chrome verification covers a new tab by default, a separate window after saving
the preference, persistence through Launcher reload, and switching back to tabs.
The shared Preferences mobile capture was inspected.
