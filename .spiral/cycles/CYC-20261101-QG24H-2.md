## Original Analyze and Plan (superseded)

The maintainer agreed to the proposed next goal: Launcher asks an already-open
Files app to select a resource; the selected URL appears in Launcher's resource
field. This continues broker roadmap Phase 0 contract work and the Phase 1
two-app proof. Provider discovery and cold startup remain deferred.

Current behavior: Files lists folders and downloads files, but has no request
or result selection mode. Launcher takes manually entered resource URLs. There
is no capability broker, client, registration or request transport in the
current apps/packages. Existing launch URLs convey context, not live results.

Commitment: the proposal stated this gap, the cross-origin observable outcome,
scope and alternatives; the maintainer answered "agreed". No second goal
confirmation is required. Architecture philosophy and Muze culture favor small,
replaceable mechanisms and keeping policy in this suite. The adopted warning
profile calls for checking authority and composed behavior: broker identity
must not be inferred from an unverified WebID, and returned URLs grant no access.

Plan: define the browse contract and explicit broker routing/authentication;
add a self-hostable service, a small client and app-owned picker UI. Use the
existing linked preferences for the broker URL. Prove selection, cancellation,
disconnect, denied access and preservation across distinct app origins.
Authentication uses explicitly provisioned per-application broker credentials,
scoped to an origin, workspace and allowed routes, independent of Pod login.
Credentials are entered for each app connection and not saved in Pod data.

Non-goals: discovery, provider cold launch, app catalogs, new apps, collaboration,
automatic sync/PWA rollout, Solid delegation and publication. The recipient
pilot contract can be documented, but its implementation remains Phase 3.

Evaluation: browser proof through the real broker, negative routing/auth tests,
existing suite checks, mobile UI review and gzip measurement including shared
dependencies. Read-only baseline: Launcher 114725, Contacts 114491, Files 97344,
Profile 114361 gzip bytes using the current build settings; no optimization
change was needed to establish this baseline.

Pause/replan if secure scoped routing requires granting the broker Pod access
or if the provider must rely on shared browser storage between origins.

## Original Evaluate (server proof; superseded)

The real browser/service proof passes between two app origins. Selection puts
the URL into Launcher without a download or Pod write. Provider and caller
cancellation preserve the existing field. Denied folder access terminates the
request visibly, and provider disconnect rejects it. A second simultaneous
request gets a busy response without displacing the pending selection.

A separate minimal browser consumer imports the client with no renderer,
connects on a third origin, closes every Launcher tab and completes a Files
selection. This directly tests independence from Launcher as a routing/lifecycle
owner. Protocol tests also cover wrong origins/credentials, unauthorized
registration/routes/responses, privacy of event queues, provider ambiguity,
timeout, shutdown and connection-attempt cancellation.

Verification on 2026-11-01: `npm run check`, `npm run test:browser`, direct
`node test/capabilities.test.mjs` (seven cases), snapshot validation and

390px viewport has no horizontal overflow. Setup is documented in

Browser verification initially exposed incorrect row-control placement and

Plan continuity: this advances the Phase 1 communication proof and documents

## Revised Act and Evaluate: browser-local workspace

The maintainer's confirmed revision removes the relay service and connection
panel. Launcher owns fresh app instances and exact origin/window-bound private
ports, with explicit per-instance browse grants. Published Solid Workspace
IndexedDB stores account-scoped state locally. The Pod receives a conditional
native Turtle checkpoint only at explicit save/close, or a prepared best-effort
keepalive attempt on browser closure. The implementation is `101a053`; revised
verification is EVD-20261101-QG24H-10.

Existing app workflows and the cross-origin managed-workspace fixture pass.
Tests demonstrate selected resource/cancel, distinct app states, reload without
duplicates, local-only updates, acknowledged conditional Pod save, fresh-browser
Pod restoration and closure of participating children. Failed/conflicting/offline
saves retain local data and leave apps open. Profile field drafts restore without
replacing native RDF. The mobile picker has no overflow at 390px, and all app
JavaScript graphs including authentication stay below 200000 gzip bytes.

Chrome 131 received an authorized close-time write in the isolated fixture;
the result is explicitly distinguished from acknowledged saves and real-provider
OIDC/DPoP verification. Browser-X persistence is not guaranteed. Popup policy,
COOP and nonparticipating external apps limit lifecycle restoration. Named
workspaces, automatic app-data sync/PWA rollout and recipient/provider discovery
remain future work. The earlier Launcher-closed criterion belongs to the
superseded server design and is not current acceptance evidence.

Manual actual-Pod verification and human evaluation remain pending. The cycle
stays Active on its branch. Changes are committed for review; no merge or
publication is authorized or performed.
